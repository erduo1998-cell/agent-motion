# 把设计决定映射到引擎

本表映射概念与核验位置，不提供通吃所有版本的 API。先读项目配置、已装版本和既有实现；沿用项目入口，再应用设计规则。MiniMag X3 或其他本地项目必须读取自身文档，不能依据名字推断能力。

## 先核实当前工程能力

从现有配置、代码和真实输出核实本次用得到的能力，不另写能力记录：

- 实际引擎/版本、渲染器、画幅/分辨率/帧率、时间单位。
- 是否有真实三维几何，或只有空间中的平面、分层图片与 CSS 变换。
- 输出相机如何选择；对象、相机和父级各由谁控制。
- 投影方式、裁切范围、阴影/景深/运动模糊是否支持；预览和最终渲染是否不同。
- 文本最终由哪个系统渲染，字体是否已加载，测量的是实际字形还是估计值。

已有证据足够就直接用；不为填完整表格而扫描无关项目。

## 跨引擎概念表

| 设计意图 | After Effects | Blender | Three.js / WebGL | 其他项目的核验问题 |
|---|---|---|---|---|
| 平面/分层/实体 | 普通 3D 图层可仍为平面；挤出或模型需对应能力 | 平面与实体几何分开选择 | 平面几何与实体几何分开选择 | 是真实几何、卡片还是整体合成图？ |
| 透视与正交 | 相机设置决定取景；工作正交视图不自动成为输出相机 | Camera 的 Perspective / Orthographic | `PerspectiveCamera` / `OrthographicCamera` | 投影方式可设置还是固定？ |
| 前后层与遮挡 | 3D 图层 Position；预合成/中间 2D 层可能改变交互 | 物体位置、可见性、合成关系 | 场景深度与材质/合成顺序共同核实 | 深度决定遮挡，还是只有绘制顺序？ |
| 相机转向与位移 | Camera Position、Orientation/Rotation、Point of Interest | 相机对象的变换；目标跟随看现有约束实现 | 相机变换与取景目标；查项目已有控制器 | 相机真在移动，还是整体图在变换？ |
| 相机与主体分控 | Camera / Null / 图层父子关系 | 相机、物体、父级/约束关系 | 相机、对象与父级；避免控制器和时间线争写 | 同一属性是否被多个系统覆盖？ |
| 取景与比例 | Zoom、Angle of View、Focal Length、Film Size | Lens/FOV、Sensor、输出画幅 | `fov`、`aspect`、投影边界或 `zoom` | 参数单位、视角轴和输出比例是什么？ |
| 裁切 | 核实使用的相机、合成边界和实际渲染支持 | Clip Start/End 与 Camera view | `near` / `far`；动态取景需重验 | 对象接近镜头时何时消失？ |
| 接触与阴影 | Light、Material Options、渲染器支持 | 光源、材质、承接面与当前渲染器 | 渲染器、光源、投射/接收对象、阴影覆盖分别核实 | 用实时阴影、烘焙还是有意的简化图形？ |
| 景深与焦点 | Focus Distance、Aperture/F-Stop；实际支持依渲染器 | Depth of Field、Focus Object/Distance、F-Stop | 核实后处理/渲染管线；普通透视相机并不自动提供景深模糊 | 模糊是深度相关还是整层滤镜？ |
| 场景文字/屏幕注释 | 3D 文字层与 2D 叠加层分开安排 | 场景文字与后期文字按工程设置分开 | 场景对象文字与 DOM/独立叠加通道分开 | 文字应随场景透视/遮挡，还是固定屏幕？ |
| 可重复时间采样 | 合成时间及关键帧/表达式 | 帧/子帧及动画数据 | 项目时间到状态的映射，避免仅依累计帧数 | 同一时刻重复寻址是否得到同一画面？ |

依据：SP-A/B/D/G/H/I；父级争写、重复采样和能力核实是本 Skill 的工程检查，不是这些页面的统一实现规范。Blender 概念依据已读取的 4.3 手册；实际版本仍需核实。

## 坐标转换合同

跨项目先约定以下含义，再转换数值：

| 层次 | 应明确的含义 | 常见错误 |
|---|---|---|
| 世界空间 | 单位、上方向、前方向、原点 | 直接复制另一软件的 XYZ |
| 对象局部空间 | 原点/锚点、父级、旋转顺序 | 以为旋转围绕视觉中心 |
| 相机空间 | 朝向、正向深度、投影类型 | 把世界 Z 的正负当远近 |
| 屏幕空间 | 像素或归一化坐标、左上/左下原点 | 切镜时物体世界同向但画面反向 |
| 时间 | 秒/帧、帧率、区间端点、插值含义 | 把帧数原样复制到不同帧率 |

为检查画面可约定 `u=x/W, v=y/H`，原点设为左上。这只是检查坐标；不要因此改写引擎本身坐标系。输出方向应从最终相机投影判断。

AE 文档中 XY 原点及正方向与其他三维软件可能不同；Blender/Three.js 的项目还可能设置自定义父级或轴转换。没有确认前，不规定固定符号翻转表。

## 两个可用的几何诊断

这些是理想投影关系，用于排错，不是“美观阈值”。

1. **视差**：固定朝向、固定焦距的透视相机横移，静止点的屏幕位移量与正向相机深度大致成反比。若近远平面等速黏在一起，检查投影、分层和是否只动了整图。纯旋转或正交不能这样判错。
2. **参考帧尺寸补偿**：正对相机的平面从深度 `d` 移到 `d'`，保持参考帧投影尺寸可用 `scale' = scale × d'/d` 起步。相机轨迹、倾斜、遮挡改变后仍须看实际预览。

Three.js 官方相机文档要求相关投影参数改变后调用 `updateProjectionMatrix()`；这不是每次对象平移都要做的动作。使用封装框架时先查是否已经代办。

## 能力缺失时的降级顺序

先保留信息结构和运动意图，再改变技术手段：

- 没有实体三维但只需轻微视差：分层图片或平面足够；不要承诺不存在的背面。
- 没有真实景深：先用遮挡、尺度、明暗区分；有意的分层模糊需标明并检查边缘，不伪称光学景深。
- 实时阴影成本过高：按风格用烘焙/简化接触阴影，确保与主体关系一致。
- 没有相机：可用组变换或显式分层运动实现部分观看变化；全组同速平移不会自动产生透视视差。
- 平台预览与最终输出不同：先验证最有风险的短段，再扩大；不能用编辑器视图代替最终相机证据。

只调整本次需要的能力。不要为使用本 Skill 重建整条渲染管线。

## Three.js 新镜头的最短构图接入

若本次方案指定了物体在屏幕中的位置/占幅，使用 [three-frame 适配器](three-framing-adapter.md) 可以直接把真实 Object3D bounds 与目标框解成相机。它适用于新建的对称透视镜头，不接管工程时间线，也不替代 AE/Blender 的原生关键帧与约束。
